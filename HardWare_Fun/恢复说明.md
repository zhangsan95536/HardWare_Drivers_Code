## 一、结论先讲

| 问题 | 答案 |
|---|---|
| 文件夹为什么突然变成"文件"？ | 它在 FAT32 根目录里的 32 字节目录项，**属性字节从 `0x10`（目录）变成了 `0x00`（普通文件）**。名字、簇号、大小都还在，只是"我是文件夹"这一个标志位丢了，于是 Windows 把它当成了一个 8192 字节、打不开的坏文件。 |
| 数据丢了吗？ | **基本没丢。** 该文件夹的目录项指向的簇（86718）以及它下面所有文件的簇都还在盘上，内容可读。 |
| 为什么打不开？ | 除了属性位，该目录簇的**后半段（offset 1152 以后）被别的文件数据覆盖**（里面混着 PDF 与 PPTX 的碎片），所以目录里第 20 条以后的条目（原本可能还有 Keil 工程文件等）已经不存在了；前面的 18 个源文件 + `OLED代码` 子目录完好可恢复。 |
| 根因是什么？ | **这根 U 盘的闪存单元已经发生位级退化**（见第五节），叠加两次 `chkdsk` 修复（盘上留有 FOUND.000 / FOUND.001 两个恢复目录，共 597 个 .CHK），最终把目录项写坏了。这不是软件误操作，也不是病毒。 |

**最重要的建议：立即把 F: 盘上所有还需要的东西拷到别的盘，然后更换这根 U 盘。** 它已经在不可逆地掉数据了，本次恢复是从它上面"抢救"出来的，不是修好了它。

## 二、现场证据

### 2.1 目标路径的实际身份

```
路径      F:\外设函数（标准库）
类型      普通文件（不是目录）
大小      8192 字节（= 1 个簇，该盘簇大小正好 8192）
属性      Normal（0x20）
创建时间  2026-10-26 10:02:35
修改时间  2026-10-24 00:34:36
```

创建时间晚于修改时间——典型的"目录项被 chkdsk 重新写过"的痕迹。

### 2.2 出问题的那个 32 字节目录项（原始字节）

它在根目录簇（簇 2）内的偏移 3040 处：

```
cd e2 c9 e8  ba af 7e 31  20 20 20 00  00 b5 51 50
5a 5d 5c 5d  01 00 52 04  58 5d be 52  00 20 00 00
```

| 字段 | 值 | 应有值 | 说明 |
|---|---|---|---|
| 8.3 短名 | `ÍâÉèº¯~1`（GBK 的"外设函~1"） | 同 | 正常 |
| 属性 attr | **`0x00`** | **`0x10`** | ★ 就是这里坏了：DIR 位丢失 |
| 首簇 | 86718 | 86718 | **正确**，指向真正的目录数据 |
| 文件大小 | 8192 | 0（目录项大小应为 0） | 被写成了 1 个簇 |
| 长文件名 LFN | "外设函数（标准库）" | 同 | **完整未损坏**，所以名字显示正常 |

只要把 attr 的 `0x00` 改回 `0x10`、size 改回 0，Windows 立刻又能把它当文件夹打开——但那样会带着一堆被覆盖的坏条目、并且要往坏盘上写数据，**有覆盖剩余可恢复数据的风险**，所以本次没有做原地修复，而是全程只读地把数据提取出来重建。

### 2.3 目录簇本身被"交叉链接"覆盖

目录簇 86718 共 36 条 32 字节条目：

- 偏移 0 起：`.`、`..`（这两个的簇号字段也已损坏）
- 偏移 96 ~ 1120：**18 个真实文件 + 1 个子目录 `OLED代码`**，条目基本完整
- 偏移 ≥ 1152：**不再是目录项**，而是别的文件的内容被写进了这一簇：
  - PDF 片段：`8378 0 R/Type/Page/Contents`、`null]/Border[0 0 0]/Subtype/Link/Rect[...]`
  - PPTX/ZIP 片段：`ppt/slides/slide1.xml`、`[Content_Types].xml`

也就是说，FAT 表把这个簇同时分给了两个文件（目录和某个 PPT/PDF），后写的那个把目录的后半截冲掉了。

### 2.4 chkdsk 已经跑过两次

| 目录 | 时间 | 内容 |
|---|---|---|
| `F:\FOUND.000` | 2026-10-27 16:20 | 238 个 `FILE0000.CHK` … |
| `F:\FOUND.001` | 2026-10-28 11:08 | 359 个 `FILE*.CHK` |

共 597 个 CHK、35,364,864 字节。这说明该盘的文件系统此前已经至少两次被判为"不一致"，chkdsk 把找不到归属的簇统统倒成了 .CHK。本目录里的源文件，有一部分在 CHK 里能找到同样受损的副本（见 4.3）。

## 四、做了哪些修复

原始提取出来的字节里散布着大量位级错误（`#define`→`#defile`、`#ifndef`→`#mfndef`、`GPIO_InitTypeDef`→`GPIO_HnitTypeDef`、`RCC_APB2PeriphClockCmd`→`RCC_APB2PuriphAlockCmd`…），所以做了以下修复：

### 4.1 四份工程冗余对照（最有效）

四套工程里有大量同名同内容文件，利用"多数决"互相纠错：

| 手段 | 结果 |
|---|---|
| 四份逐字节三取二投票（跳过 Hardware/、User/） | 修好 **30 个文件、41,324 字节**（`stm32f10x.h` 一个文件就修了 21,514 字节） |
| 选"损坏最少且两份完全一致"的版本当真值 | 再修 9 个文件 |
| 全工程（含 Hardware/、User/）等长副本互修 | 再修 `stm32f10x_conf.h`、`stm32f10x_it.c` |
| 已知坏行定点修复 | 8 处 × 4 份 = 32 处（`\x0f`、`\x08`、`\x10`、`\x03`、`\x1f`、`\x01` 等单字节注入） |

### 4.2 跨编码恢复 OLED.C

`UTF-8\01\Hardware\OLED.C` 是四份里唯一完全干净的（52929 字节）。把它按 GBK(936) 转码后**恰好 44967 字节**，与 `GB2312\01` 目录项里记录的原始大小完全吻合——据此确认二者是同一份源码，并用转码结果直接重建了 `GB2312\01\Hardware\OLED.C`。

### 4.3 尾部清理与重建

- `led.c`、`bsp_i2c_gpio.c` 按最后一个 `}` 截断，去掉簇尾的残留数据
- `pwm.h` 原文件只剩 6 行（`#endif` 已损坏），按 `pwm.c` 里的真实调用签名重建（154 字节）
- `使用说明（必读）.txt` 目录项声明 110 字节是坏值，实际正文 480 字节后接 `0xFF` 擦除填充，已按填充截断（112 字节）
- `bsp_hcsr04.h`、`buzzer.h`、`motor.h` 去掉尾部 NUL 填充

### 4.5 hal库两份 OLED.C 的函数级重建（2026-10-28）

这两份文件的**硬件层本来是完好的**（`SoftWare_IIC` 的软件 I2C：`OLED_W_SCL` / `OLED_W_SDA` / `OLED_I2C_Start` …；`HardWare_IIC` 的硬件 I2C：`HAL_I2C_Mem_Write` / `OLED_I2C_ADDRESS` …），坏的只是中间"显存绘制"那一段：

| 文件 | 坏字节区间 | 坏行区间 |
|---|---|---|
| `hal库\SoftWare_IIC\OLED.C` | 23,601 – 39,805 | 684 – 1,014 |
| `hal库\HardWare_IIC\OLED.C` | 15,361 – 31,724 | 493 – 788 |

关键依据：这个驱动的**显存绘制核心与硬件无关**，且与干净样本 `标准库\UTF-8\01-OLED功能函数测试-4针脚I2C接口\Hardware\OLED.C`（52,929 字节，0 坏字节）**逐字节同源**——`OLED_ShowChar`、`OLED_DrawArc`、`OLED_SetCursor` 起始的整段直接比对 0 差异。因此按函数边界重建：

- **头部**（含硬件层、`OLED_Init`、`OLED_GetFrameBuffer`）：保留原文件，损坏 0 行
- **中部**（`OLED_SetCursor` … `OLED_DrawLine`）：取自干净样本
- **尾部**（`OLED_DrawRectangle` … `OLED_DrawArc` + 版权注释）：保留原文件
- `SoftWare_IIC` 的 `OLED_ShowString` 保留你自己的 `int` 改造：`uint16_t i = 0,j=0;`、循环体开头 `j++;`、末尾 `return j;`（与它 `OLED.H` 里的 `int OLED_ShowString(...)` 一致）
- `HardWare_IIC` 保留了你加的内容：`////单函数版本` 的 `OLED_Update` 旧实现（注释块），以及文件末尾 `uint8_t *OLED_GetFrameBuffer(uint32_t*, uint32_t*, uint32_t*)`（NWatch 绘图层用的 128×64 1bpp 页缓冲）

结果：

| 文件 | 大小 | 行数 | 控制字节 | 大括号平衡 | 函数 |
|---|---|---|---|---|---|
| `hal库\SoftWare_IIC\OLED.C` | 52,305 | 1,473 | **0** | 190 / 190 | 36 个，齐全 |
| `hal库\HardWare_IIC\OLED.C` | 50,452 | 1,425 | **0** | 191 / 191 | 31 个，齐全 |

两份均为合法 UTF-8、结尾带版权注释；原受损文件备份在 `..\_诊断脚本\原始受损副本\`。

**需要你确认两处（各一行就能改）：**

1. `SoftWare_IIC` 的 `OLED_ShowString` 返回值语义，我按"已绘制的字符个数"实现为 `return j;`。若你的本意是返回字符串长度、或末位 X 坐标，改 `OLED.C` 里那行 `return j;` 即可。
2. `HardWare_IIC` 的 `OLED_GetFrameBuffer` 明显是后来加的 NWatch 代码（不是江协原版），已原样保留；如果它其实不属于这个驱动，删掉即可。

## 五、根因：这根 U 盘的闪存已经在退化

不是编码问题，不是程序写坏，而是**物理层面的位翻转**，证据：

1. ASCII 标记词本身被改：`#ifndef`→`#mfndef`、`#define`→`#dEfine`、`#endif`→`#eldif`、`#include`→`#inglude`/`#inchude`，`GPIO_InitTypeDef`→`GPIO_HnitTypeDef`。这类错误只可能是存储单元翻转。
2. 大小写/字符位移规律性错位：`0x20`(空格)→`0x30`(`0`)、`0x2E`(`.`)→`0x2A`(`*`)、`0x0001`→`0x4001`，都是单比特翻转。
3. NUL 字节（`0x00`）被注入到正常文本中间（317 个文本文件里 147 个含控制字节，4 份 `stm32f10x.h` 分别有 3553 / 2763 / 1947 / 503 个控制字节）。
4. 损坏**高度集中在 86718~86737 这一小片连续簇**（同一闪存擦除块 / 同一片区），而盘上其余目录（PDF 手册、PPT、zip）内容正常——典型的局部擦除块失效。
5. 该盘已有两次 chkdsk 介入记录（FOUND.000、FOUND.001），说明文件系统此前已多次不一致。
6. 读取该盘时明显变慢（提取 9 MB 花了约 20 分钟，进程 CPU 占用仅 0.03 秒，全部时间耗在等 I/O 重试上）。

## 六、怎么用这份恢复结果

1. **`hal库\SoftWare_IIC\OLED.C` 与 `hal库\HardWare_IIC\OLED.C` 现在可以直接用了**（见 4.5），把它们连同同目录的 `OLED.H` / `OLED_Data.c` / `OLED_Data.h` 一起拷进你的 CubeMX 工程即可。
2. **标准库版本先用 `UTF-8\01` 那套工程**（`Project.uvprojx` 唯一一份从头到尾干净、且 XML 校验通过的 4 针脚 I2C 版本），Keil 打开即可编译。
3. 若要 7 针脚 SPI 版本，用 `UTF-8\02`，但 `Hardware\OLED.C` 后半段有坏行需要对照修（可以拿 `UTF-8\01` 的 `OLED.C` 比对，两者前 2/3 基本一致）。
4. `Project.uvoptx` 是 Keil 的"个人视图/断点/窗口布局"文件，损坏的那两份**直接删掉**，Keil 打开工程时会自动生成新的。
5. 你原来的 `bsp_i2c.h` / `bsp_i2c_gpio.c` 请优先从旧工程备份、Git、或者当时发过的聊天记录里找原件；找不到就按 `bsp_i2c.c` 里的调用点反推接口重写。

## 七、后续建议（按优先级）

1. **立刻备份 F: 全盘**到另一个盘（约 1.06 GB，很快）。不要再往 F: 写任何东西，不要对它跑 `chkdsk /f`（会进一步改写目录项、覆盖可恢复数据）。
2. **更换这根 U 盘。** 位翻转是不可逆的，继续用只会丢更多数据。
3. 若还想从 F: 抢救别的文件，先做**整盘镜像**（如 `dd` / DiskGenius / WinHex 的"克隆磁盘"），之后所有恢复操作都在镜像上做。
4. 以后重要代码放**版本控制 + 至少两份异地备份**，U 盘只做临时搬运。
